# Decisions

There is one way to do each thing, and agents use exactly what is listed here.
To change a row, record the new decision, remove the old way from the code **in the same change**, and add a line to the log.

## Game 1: Don't Match the Host
- **Name and ID.** `game_id` is `offbeat`, and it's **permanent**: it's stored with every run, event, ledger row and content path. The display name "Offbeat" is branding and can change without a migration. (Human, 2026-10-18.)
- **Sudden death.** Matching the host ends the run; the points come from the questions survived (Scoring, below).
- **Fixed sequence.** Every player gets the same 7 questions in the same order each day, so friends' scores can be compared directly.
- **Independent questions, rising difficulty.** The day's questions are unrelated to each other and mix concrete ones (a clear answer set, e.g. days of the month) with abstract ones (e.g. something you'd bring to a potluck). Difficulty is the share of players the host's answers would catch. It rises gently through the day, so the number of host answers varies by question (1 of 12 zodiac signs catches about 1 player in 12; for a skewed question like "an animal", it depends on how popular the host's pick is). The game is casual: most players should usually finish, but difficulty may vary from day to day, and a hard day is welcome. Catch rates are estimates until the closed beta measures them (M15; the beta is the live playtest, human, 2026-10-20). The M02 2g survey gave a first, small sample, and tuning is M13 (2026-10-21 docs audit). (Human, 2026-10-18. This replaces the narrowing chain and the "question k has k host answers" rule.)
- **Timer.** Each question gives 20 seconds, from Start (question 1) or from Next after the reveal (the rest; M04 13c-4); when they run out, the run ends (human, 2026-10-21; M04 13c-2). The database is the judge: `private.question_deadline` holds the 20 seconds, the answer trigger refuses a late answer, and the status view shows the run as timed out. The client only displays the time left that the server measured. **Midnight doesn't end a run:** a run started before the reset can be played to its end after it, and its points count like any other run's, for the day it was played (human, 2026-10-22, M09 D1: "a run's points count whenever it's finished, for its own day, and a run that's never finished counts nothing"; it replaced the 2026-10-21 rule that such a score doesn't count). So no run is "abandoned" any more: a run ends with a catch, its last question, or a question's time running out, and a run left at a reveal stays in progress until the player taps Next (M04 13c-4); a reload resumes it, even after midnight ("Resume yesterday's run", human, 2026-10-21). A run left at a reveal scores nothing until the player comes back and finishes it; one never finished never scores (M09 D1).
- **Scoring:** surviving questions 1 to 7 earns 25, 50, 75, 100, 150, 250 and 350 points (human, 2026-10-21, M04 G1: points rise with each harder question in growing jumps; `POINTS_PER_QUESTION` in `tunables.ts`). It replaced k points for question k (proposed by Claude, accepted by a human, 2026-10-17). A run that ran out of time scores the questions it survived, like a caught run (human, 2026-10-22, M09 D2). **Rarity bonus** (human, 2026-10-22, M09): each survived answer also earns a bonus that's bigger the fewer players gave the same answer to that question that day, counted among the players who answered it. Each answer starts from an expected share (for now, the day's host bank is the common tier and every other answer uncommon: M09 D11), and the day's real counts are blended in. The player sees a provisional bonus at once, from the expectation alone; the final one uses the answers recorded before the day's midnight. Answers given after midnight earn no bonus (M09 D8). A run's bonus is always less than the points of the first question it didn't survive, so getting further always beats rarer answers; a perfect run's bonus has its own cap. So 1000 is no longer the maximum; comparing games is planned with daily percentiles (draft M16). The weights, the formula and the caps are numbers the human gives (M09 ticket, Numbers).
- **Server is authoritative.** The client never receives host answers, or anything that marks the host bank, before the player answers that question.

### Answer model (confirmed)
| Bank | Contents | Sent to client? |
|---|---|---|
| Accepted bank | As complete as practical, so players can escape with niche answers. Concrete questions are built from reference lists; abstract ones (e.g. "something you'd bring to a potluck") are curated and grow from logged misses (M02). One level of detail per question: don't list an answer next to "<kind> <answer>" variants of it (e.g. "cake" with "chocolate cake"). Differently named kinds may sit next to a general answer ("tuna" next to "fish"), but a general answer is never a host answer when its kinds are listed. (Human, 2026-10-18) | Never: the list was a free hint (human, 2026-10-21; M04). The client sees only the entry it typed, after answering |
| Host bank | A small subset of common, typical answers | Never, and nothing marks which entries are in it |
| Host answer(s) | Picked from the host bank | Only after the player has answered that question |

- **Canonical entries.** Each entry has an ID and aliases (plurals, alternate spellings, synonyms). **The client sends the typed text** and the server alone turns it into an entry (human, 2026-10-21; M04 13c-1; `src/game/matching.ts`, `resolveTyped`): an exact name or alias after normalization first, otherwise text of 4+ letters one typo from exactly one entry. Text that close to no entry, or to two (the server would be guessing which one), is "not in our list, try again": a free retry, logged as a miss (human, 2026-10-21: "The two-entries typo rule is fine as built"). Matching compares IDs.
- **Match groups.** Only for answers that really are the same thing in a player's eyes. Kinds and look-alikes are separate answers that don't match (a Ferris wheel isn't a wheel), and with one level of detail per question most questions have none (human, 2026-10-18). It's a match when the player's entry is the host answer itself or is in the host answer's group. **A host answer always matches itself**, so its group lists only the other entries it covers, and listing it inside its own group is a content error (human, 2026-10-18; M01 review).
- **Normalization** (case, whitespace, punctuation, diacritics) and **plural aliases** are applied when content is authored, by a deterministic step that a human reviews. At runtime the typed text gets the same normalization and the one-typo rule above, and nothing else is guessed.
- **Niche answers are an intended escape** (human, 2026-10-18), similar to Krillion's rare-answer play. The remaining risk is a list missing a fair answer. Text that names no entry is a no-penalty retry that logs the typed text, so a human can grow the lists.
