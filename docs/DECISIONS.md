## Game 1: Don't Match the Host
- **Name and ID.** `game_id` is `offbeat`, and it's **permanent**: it's stored with every run, event, ledger row and content path. The display name "Offbeat" is branding and can change without a migration. (Human, 2026-10-18.)
- **Sudden death.** Matching the host ends the run, and the score is the number of questions survived.
- **Fixed sequence.** Every player gets the same 7 questions in the same order each day, so friends' scores can be compared directly.
- **Independent questions, rising difficulty.** The day's questions are unrelated to each other and mix concrete ones (a clear answer set, e.g. days of the month) with abstract ones (e.g. something you'd bring to a potluck). Difficulty is the share of players the host's answers would catch. It rises gently through the day, so the number of host answers varies by question (1 of 12 zodiac signs catches about 1 player in 12; for a skewed question like "an animal", it depends on how popular the host's pick is). The game is casual: most players should usually finish, but difficulty may vary from day to day, and a hard day is welcome. Catch rates are estimates until the M02 2g survey measures them, then the M11 live test (human, 2026-10-20: the playtest moved to the MVP). (Human, 2026-10-18. This replaces the narrowing chain and the "question k has k host answers" rule.)
- **Timer.** Each question gives 20 seconds, from Start (question 1) or from Next after the reveal (the rest; M13 13c-4); when they run out, the run ends (human, 2026-10-21; M13 13c-2). The database is the judge: `private.question_deadline` holds the 20 seconds, the answer trigger refuses a late answer, and the status view shows the run as timed out. The client only displays the time left that the server measured. **Midnight doesn't end a run:** a run started before the reset can be played to its end after it, but its score doesn't count for the leaderboard (human, 2026-10-21: "they get to play the puzzle but their score doesn't contribute to leaderboard"; M08 applies the leaderboard part). So no run is "abandoned" any more: a run ends with a catch, its last question, or a question's time running out, and a run left at a reveal stays in progress until the player taps Next (M13 13c-4); a reload resumes it, even after midnight ("Resume yesterday's run", human, 2026-10-21). How a run left at a reveal scores is for M08.
- **Scoring:** surviving questions 1 to 7 earns 25, 50, 75, 100, 150, 250 and 350 points, so a perfect run scores 1000 (human, 2026-10-21, M13 G1: points rise with each harder question in growing jumps, and every game's perfect run can be the same round total; `POINTS_PER_QUESTION` in `tunables.ts`). It replaced k points for question k (proposed by Claude, accepted by a human, 2026-10-17). A run that ran out of time scores the questions it survived, like a caught run (Claude's reading of "the run ends", human, 2026-10-21; to settle with the M08 ticket).
- **Server is authoritative.** The client never receives host answers, or anything that marks the host bank, before the player answers that question.

### Answer model (confirmed)
| Bank | Contents | Sent to client? |
|---|---|---|
| Accepted bank | As complete as practical, so players can escape with niche answers. Concrete questions are built from reference lists; abstract ones (e.g. "something you'd bring to a potluck") are curated and grow from logged misses (M02). One level of detail per question: don't list an answer next to "<kind> <answer>" variants of it (e.g. "cake" with "chocolate cake"). Differently named kinds may sit next to a general answer ("tuna" next to "fish"), but a general answer is never a host answer when its kinds are listed. (Human, 2026-10-18) | Never: the list was a free hint (human, 2026-10-21; M13). The client sees only the entry it typed, after answering |
| Host bank | A small subset of common, typical answers | Never, and nothing marks which entries are in it |
| Host answer(s) | Picked from the host bank | Only after the player has answered that question |

- **Canonical entries.** Each entry has an ID and aliases (plurals, alternate spellings, synonyms). **The client sends the typed text** and the server alone turns it into an entry (human, 2026-10-21; M13 13c-1; `src/game/matching.ts`, `resolveTyped`): an exact name or alias after normalization first, otherwise text of 4+ letters one typo from exactly one entry. Text that close to no entry, or to two (the server would be guessing which one), is "not in our list, try again": a free retry, logged as a miss (human, 2026-10-21: "The two-entries typo rule is fine as built"). Matching compares IDs.
- **Match groups.** Only for answers that really are the same thing in a player's eyes. Kinds and look-alikes are separate answers that don't match (a Ferris wheel isn't a wheel), and with one level of detail per question most questions have none (human, 2026-10-18). It's a match when the player's entry is the host answer itself or is in the host answer's group. **A host answer always matches itself**, so its group lists only the other entries it covers, and listing it inside its own group is a content error (human, 2026-10-18; M01 review).
- **Normalization** (case, whitespace, punctuation, diacritics) and **plural aliases** are applied when content is authored, by a deterministic step that a human reviews. At runtime the typed text gets the same normalization and the one-typo rule above, and nothing else is guessed.
- **Niche answers are an intended escape** (human, 2026-10-18), similar to Krillion's rare-answer play. The remaining risk is a list missing a fair answer. Text that names no entry is a no-penalty retry that logs the typed text, so a human can grow the lists.
