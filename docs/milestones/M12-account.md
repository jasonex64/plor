# M12 — Account

**Status:** done (2026-10-24). 12a, 12b, 12c, 12e and 12d are merged (PRs #58, #59, #60, #62 and #63), each with the human's approval of its security changes; the ticket was PR #57.

## Goal
A player can see and manage their own account in one place: their username (and change it, if A2 allows), display name, friends and invite link, all-time points, sign-out, and deleting the account themselves. The sign-in fixes filed for M12 come with it.

## Who uses it / what breaks without it
- **Used by:** every signed-in player, now and then rather than daily: to change how they're shown, find their invite link, see their total, sign out, or leave.
- **Breaks without it:**
  - **Deleting an account needs an email to the human,** who deletes the user by hand in the Supabase dashboard (the privacy page promises it, with no written procedure: ROADMAP "Next revision", For M12). Before the beta (M15), every player needs a way to leave without asking.
  - **A username can't change.** It was an M02 scope limit, not a decision (ROADMAP, M12 row); the human asked about the tradeoffs (2026-10-21).
  - **The all-time total was taken off the leaderboard** when it went weekly, to come back here (ROADMAP "Design review", 2).
  - **Account settings are mixed into the home page** (display name, friends, invite link, sign-out), which M11 reordered around the day.
  - Four problems are filed for M12 (ROADMAP "Next revision", For M12): sign-out ends every device's session; the code form has no way back from a mistyped email and keeps a pasted space; deleting an account while someone in one of its groups leaves can deadlock; and deletion scans comments and reactions with no index.
- **The human's words:**
  - "An account page, including deleting your account" (ROADMAP, Product);
  - "all working features first. home screen friends screen groups, account etc." (2026-10-21);
  - the all-time total "moves to the account page (M12)" (2026-10-22, Design review, 2).

A route db test (`src/app/api/account/route.db.test.ts`) shows a total across weeks equal to the ledger sum, a finished run on a closed day settled first, and today's run not counted before the day closes (M09 D9); a signed-out player gets 401.
- [x] **12a** `/account` (A1) shows the username, the all-time total, the display name form, the friends list with the invite link, and Sign out; the home page's Account section is a link to it and Sign out, with the display name, friends and invite link gone from the home page (moved, not copied). Opened signed out, `/account` shows sign-in first. e2e: a player opens the account page from the home page, sees their username and 0 points, sets a display name there, and the home page shows only the link and Sign out.
- [x] **12b** Sign out ends only this device's session (A3): `signOut({ scope: "local" })`; a route db test signs one player in twice (two sessions), signs one out, and Auth still holds the other session.
- [x] **12b** The code form (A6): a "Use a different email" button goes back to the email step, and a code typed or pasted with spaces ("123 456") signs in, the route removing the spaces before Auth checks it (a route db test with a real emailed code).
- [x] **12b** The database keeps the username rule (A2; pgTAP, `supabase/tests/profile.test.sql`): `plor_app` may update `username` and nothing new besides; a change sets `username_changed_at`; a second change within 30 days of the last is refused (`OB011`); the first change after picking one is allowed at once (A2's reason: a wrong pick at sign-up can be fixed); the format and uniqueness rules still hold, and the old name is free at once.
- [x] **12b** `POST /api/profile/username` changes the signed-in player's username (route db test): the new name is shown, the old one can be taken by another player, a taken or invalid name gets 409 `username_taken` or 400 `username_invalid`, and a second change within 30 days gets 409 `username_change_too_soon`; `GET /api/account` gives the date the next change is allowed, and the account page shows it (e2e: change the name on the account page, see it, and see when it can change again).
- [x] **12c** The database deletes an account (A5, A7; pgTAP, `supabase/tests/account_deletion.test.sql`): `private.delete_account(user_id, username)` runs with its owner's rights and an empty `search_path`, and `plor_app` may execute it and gains nothing else. With the player's own username it leaves each of their groups first, the way `leaveGroup` does (the group locked, then the membership deleted), so a group they created passes to its longest-standing member and a group they were the last member of is deleted (M10 G6). Then it deletes their `auth.users` row, which removes everything A5 lists: profile, runs, answers, misses, ledger rows, their comments in both threads with those comments' reactions and reports, their reactions and reports on others, friendships both ways, invite code and admin row. Another player's rows are untouched. With any other username it deletes nothing and returns false.
- [x] **12c** No deadlock with a group leave (ROADMAP "Next revision", For M12; db test, two connections): one player, the creator of a group, leaves it in an open transaction while another member's account is deleted; the deletion waits for the group and finishes after the leave commits, with neither aborting.
- [x] **12c** The cascade has indexes (ROADMAP "Next revision", For M12): `private.comment` and `private.reaction` get an index on `(user_id, game_id, puzzle_date)`, the key their foreign key to `private.run` deletes by. Evidence: `EXPLAIN` of that delete uses each index.
- [x] **12c** A10: `plor_app`'s INSERT on `private.profile` is `(user_id, username)` only (pgTAP grant list); creating a profile as `plor_app` still works, and naming `username_changed_at` in an insert is refused (`src/lib/profile.db.test.ts`).
- [x] **12c** `POST /api/account/delete` with `{ username }` (route db test): a signed-in player who types their own username gets 200, their account is gone, and this device's session cookies are cleared (A9 (a); `signOut({ scope: "local" })`, which ignores Auth's answer for a user who no longer exists, auth-js 2.118.0 `_signOut`). Any other username, or none, gets 400 `username_mismatch` and deletes nothing; signed out gets 401.
- [x] **12c** A deleted player's leftover access token can't write (A9 (a); db test): for a user ID whose `auth.users` row is gone, creating a profile, starting a run, making an invite link, creating a group and posting a comment each fail and store nothing. Tested on the write functions, not the routes: the local stack signs with HS256, so its `getClaims` asks Auth and already refuses the token, while the hosted project's ES256 check would let it through to them.
- [x] **12c** The account page (A4; e2e): Delete account has a box to type your username, and the button stays disabled until the box matches it. Deleting signs you out on this device: the page shows sign-in, and so does the home page.
- [x] **12c** The privacy page (A8) says you can delete your account yourself on the account page, keeps the email address for anything else, and its date changes.
