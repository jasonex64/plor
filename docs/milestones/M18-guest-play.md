## Goal
Anyone can play today's game 1 or game 2 from the front page without an account; they see their result once, and nothing about them is kept except their answers, with no one attached.

## Who uses it / what breaks without it
- Used by: friends invited to the closed beta who want to try the game before making an account; anyone who opens a group invite link and wants a look first.
- Breaks without it: the front page asks every visitor to sign in before they can see the game (read 2026-11-11: `src/app/home.tsx:247-258`, `Signed` shows only `SignIn` when signed out). An invited friend who won't make an account just to try it never plays, and never sees what an account adds.

## Design (proposed)
**What a guest can reach.** The front page, both game routes, a run, the result with a share button, and the peek. Not friends, groups, comments, reactions, the feed, boards, Me or settings. A guest has no name, no points ledger row, no streak.

**Why not Supabase anonymous users.** They would put a row in `auth.users` for every guest, which nothing cleans up (source: "currently not available"), share Auth's 30-per-hour-per-IP limit with real sign-ins (our server calls Auth, so every guest would count as Vercel's one address; compare `src/lib/auth-limits.ts:2-4`), and every account route would have to learn to refuse a guest. Answer 9 keeps nothing about a guest, so they need no account. Trade-off: we build our own small run store (below). If the human prefers Supabase's guests, this ticket is rewritten; nothing here is shared with it.

**How a guest run is stored: separate guest tables (recommended).** Read 2026-11-11, the run rules sit on tables keyed by `auth.users`: `private.run` has `user_id uuid not null references auth.users` in its primary key (baseline, line 163); `run_event` and `question_open` follow it; the order, time and "over" rules are triggers on those tables (`check_run_event`, `check_question_open`, baseline lines 962 and 997); `run_status` is a view over them; the live-board broadcast fires on every insert (baseline lines 2970-2978); `settleRuns`, `delete_account` and every board read assume a player. So:
- *A. Separate guest tables (recommended):* `private.guest_run` (token hash, game, date pinned by `private.today()` at start, `started_at`), `guest_run_event`, `guest_question_open`, and for game 2 `guest_round_word` and `guest_round_reject` (the lockout reads it) with the same shapes as game 2's `round_word` and `round_reject` (`supabase/migrations/20261107105151_game_2_rounds.sql:18-40`), and a `guest_run_status` view as `run_status`. No foreign key to `auth.users`, no board broadcast, no ledger, no `delete_account` path. Trade-off: the order and clock rules (OB002, OB003, OB005, OB006, and game 2's lockout and round rules) must be written again for these tables. To stop the two copies drifting, 18b writes each rule as one function that both triggers call, and pgTAP runs the same cases on both. That edits the baseline's functions, so it is part of the security review.
- *B. A nullable owner in the existing tables:* one set of rules. Rejected: the owner is in the primary key, and every board, settle, comment and delete read would need a "not a guest" filter. One missed filter shows a guest as a player. That is the failure the lead's direction wants impossible.
- *C. The whole run held in a signed cookie, no guest table:* nothing to purge. Rejected: a guest can send an old cookie again to undo a death or answer a question twice, and one bot check could start unlimited runs. The server must hold the run to check it "exactly like a signed-in run".

**The token.** *Changed in 18a (4b).* The app makes it with `randomBytes`, written in base64url, as it makes invite codes (`newInviteCode`, `src/friends/friends.ts:18-20`: a `gen_random_bytes` migration and the app make them the same way, baseline lines 551-553), and stores only its hash, made by the existing `hashKey` (SHA-256, hex; `src/lib/auth-limits.ts:24-26`) in the shape `private.auth_attempt` already checks (`key ~ '^[0-9a-f]{64}$'`, baseline line 116). One way to make and one way to hash a random token, not a new one. The draft's `gen_random_uuid()` is dropped: PostgreSQL's page says it "returns a version 4 (random) UUID" and says nothing of a cryptographically strong source (read 2026-11-11), and a token that is a login for a run needs that. The invite code's length (10 characters, 60 bits) was chosen for a link that adds a friend and is not reused. The route sets it in a cookie with `httpOnly`, `secure`, `sameSite: "lax"`, `path: "/api/guest"` and no max-age (a session cookie), following the Next.js `cookies` page above. Because the path is `/api/guest`, the browser doesn't send it to account routes; and account routes read only the Supabase session through `requireUserId` (`src/lib/auth.ts:36`), which stays untouched. A guest token is never an account's ID and no account route reads it. Guest routes never call `requireUserId` and read no Supabase session. **Settled (answer 21):** the token is 20 random bytes, 160 bits, the size OWASP's Session Management Cheat Sheet prefers for a verifier stored as a hash; the same page asks that the ID be meaningless and come from a CSPRNG (`randomBytes`), and that its cookie be `Secure` and `HttpOnly`, as designed here.

**Guest routes (new, separate):** `/api/guest/run`, `/start`, `/answer`, `/next` for game 1 and `/api/guest/substrings/...` for game 2, each wrapped by `handle` and `checkProtocol` like today's. The screens call fixed `/api/run...` paths today (`src/app/game.tsx:65, 92, 194, 210-212`; `src/app/home.tsx:555, 598`; `src/app/shell.tsx:344`), so 18c gives the game screen one prefix to pick the route family; *unverified* how much of `game.tsx` assumes a profile until 18c reads it.

**Same rules as a signed-in run.** The matching, stolen letters, host answers and 20-second clock are the same functions (`resolveTyped`, `stolenLetters`, `private.question_deadline`). One run per token and game; starting again while one is open returns it (as `startRun`, `src/game/runs.ts:194`). After a run ends, a new start needs a new bot check and a new run: replay freely (answer 13). Deviation from game 1's "resume yesterday's run" (`runs.ts:175`): a guest run left over midnight is not resumed; it is purged. **A retry after the end:** DECISIONS.md's Run events row says a retry returns the stored result. A guest run's rows are deleted when it ends, so a retried final answer finds no run and gets the plain refusal 409 `run_over` (as `runs.ts:278` and `305` give for a signed-in run that is over), a 4xx, never a 500; the stored-result retry stays for signed-in runs.

**What is kept: a tally with no run.** Rarity reads only counts per (category, entry) and per (day, question, entry), never a player: `pooledCounts` groups `private.run_event` by category and entry (`src/game/ledger.ts:70-90`), `dayCounts` by day, question and entry (`ledger.ts:94-106`). So each guest answer adds 1 to `private.guest_tally (game_id, puzzle_date, question_idx, entry_id, matched, n)`. **Who increments it:** a trigger on `guest_run_event`, running with its owner's rights and an empty `search_path` (as the baseline's other guarded functions, e.g. `take_auth_attempt`, baseline line 1050), in the same statement as the event row, so a retried answer (the event's primary key refuses a second row) never counts twice, and `plor_app` needs no write grant on the tally at all. **The midnight rule, stated at the increment:** the trigger adds 1 only when `private.day_of(now()) = new.puzzle_date` (`private.day_of(timestamptz)`, baseline line 888), the same test as the players' `private.day_of(e.created_at) = e.puzzle_date` (`ledger.ts:76` and `98`; `run_event.created_at` defaults to `now()`, baseline line 181). The tally has no time column, so the rule cannot be applied when it is read; applied at the increment, a closed day's counts never change after `settleRuns` may have written its ledger (`ledger.ts:1-9`). (As ROADMAP's Next revision already notes for players, `now()` is the transaction's start, so an answer begun just before midnight and committed just after counts.) `matched` is the same flag the event row holds; it says nothing about a person, and Insights need it (below). The tally holds no run, token, time or order. It is a counter rather than one row per answer, so row order and timestamps can't be used to rebuild a run. `pooledCounts` and `dayCounts` then add `guest_tally` to what they read, so answer 7 holds for the provisional bonus, the final bonus, and the "how many gave this answer" shares. Guest answers don't go through `settleRuns`: there is no ledger row to write.

**Insights include guests (answer 22).** Read 2026-11-11, `src/insights/queries.ts:38-47` and `src/insights/report.ts`: Insights read, for one day, every `private.run_event` row (`question_idx, entry_id, matched`), every `private.missed_answer` row (`question_idx, typed`) and the names of the answers and host answers (`thingNames`); `buildInsights` turns them into, per question, `answered` (the row count), `caught` (rows with `matched`), `catchRate`, `tooFew` (`answered` under `INSIGHTS_MIN_PLAYERS`), `topAnswers` (counts per entry), `breaksShape` (a drop in catch rate against an earlier question) and `misses`. From `guest_tally` the build adds each row's `n` to `answered`, to `caught` where `matched`, and to the entry's count in `topAnswers`; the catch rate, `tooFew` and `breaksShape` follow from them. That is why the tally keeps `matched`: the draft's key (question, entry) alone cannot say caught from survived without re-running the catch rule over the base for every entry, whose answer can change after the day (DECISIONS.md, Answer model, "Fixed when the day starts"); the flag is the one the answer was judged with. **What cannot include guests:** `misses`, because a guest's misses are not kept (answer 19), and any number per run (how far runs got, a finish rate), because the tally has no run. The page says its counts include guests, who can replay (wording is the build's). The admin route reads the tally with `plor_app`'s select grant; no player ID is selected, as before (M03 D4).

**Game 2 has no rarity count.** Read 2026-11-11: `src/game/substring-runs.ts` and `substring-state.ts` read only the player's own `round_word` rows, and its standing is a percent among finished players' scores, not a count of words. So a guest's words leave nothing behind, and no `guest_round_word` or `guest_round_reject` row outlives the run. A guest sees game 2's percent among players, read only (answer 20).

**When a guest run ends, what is discarded.** The run rows (`guest_run`, events, opens, round words) are deleted when the run is over, in this order: (1) the answer or try that ends it (a catch, the last question or round) builds the result, returns it once, and deletes the run's rows in the same transaction; (2) a run whose clock ran out is found over on its next read (`timed_out`) and deleted the same way; (3) every guest start first deletes every guest run of a day that has closed (midnight Pacific, `private.next_reset`), because nothing is scheduled in this app (`ledger.ts:1-9`) and a reveal has no clock (`runs.ts:130`), so a run left at a reveal never ends by itself. This needs no new number. The cost: an abandoned run's rows, which link a hashed token to its answers, can sit up to the end of its day. They never join the tally with a link. The human accepted that (answer 17). **How the rows are deleted, with no delete grant:** two functions, `private.end_guest_run(token_hash)` (one run, found by its hash) and `private.purge_guest_days()` (every guest run whose `puzzle_date` is before `private.today()`), each `security definer` with an empty `search_path`, execute granted to `plor_app`. They delete from `guest_run` only; the children (`guest_run_event`, `guest_question_open`, `guest_round_word`, `guest_round_reject`) go by `on delete cascade`, which Postgres runs with the table owner's rights, as `run`'s children do today (baseline line 183). So `plor_app` holds no delete on any guest table. Recommended over a table delete grant because a bug in a route, or SQL run as `plor_app`, could then delete any row of any guest table, where the functions can delete only one named run or the runs of a closed day. The `plor_app` role has only select and insert on the player run tables today (baseline lines 2859 and 2875), and the guest grants are no wider than those.

**The bot check.** The guest start route reads a Turnstile token from the browser, posts it with the secret to Siteverify, and creates the run only on `success: true`. A failed check, a repeated token (`timeout-or-duplicate`), a missing token, or Siteverify being unreachable (network error, non-200, bad JSON) each stop with an error and create nothing: 400 `captcha_failed`, or 503 `captcha_unavailable` for unreachable, logged and counted (`log.warn`/`log.error`, as `authFailure` does, `auth.ts:47`). No silent pass. The widget is Managed mode (answer 16) on the guest start button; its script loads from `challenges.cloudflare.com`. No Content-Security-Policy was found in `next.config.ts`, `vercel.json` or `src` (grep 2026-11-11); if one appears later it must allow that host. Only the start is checked: the run token is the proof afterward. Keys: the site key is public and the secret key is a server-only variable in `src/config/env.ts`, which refuses to boot when any of three is missing (`TURNSTILE_SITE_KEY` and `TURNSTILE_SECRET_KEY`, named by the orchestrator, 2026-11-11, like `SUPABASE_PUBLISHABLE_KEY`, and `TURNSTILE_ALLOWED_HOSTNAMES`, answer 25; the site key reaches the browser at runtime from the server, not as `NEXT_PUBLIC_`); local and CI use Cloudflare's published test keys (values are in the Turnstile testing page, not secrets). The widget and routes are not split: the start route is born with its check, so no guest route is ever reachable unchecked.

**Answer length (audit W1).** `/api/run/answer` checks `text.trim() === ""` but no length before matching (`src/app/api/run/answer/route.ts:13-14`); the only 40-character rule is the table check `missed_answer_typed_length` (baseline line 488), reached after matching, and a hard-coded `> 40` in `reportTestMiss` (`runs.ts:419`). The guest answer route refuses text over 40 characters with 400 `text_invalid` before any matching. The signed-in route gets the same refusal in this PR, through one shared check (answer 23). *Unverified:* JavaScript length counts UTF-16 units and Postgres `char_length` counts characters, so 18c compares them with an emoji case.

**Guest misses.** Text that names no entry is a free retry and not stored for a guest. Signed-in misses feed learning by distinct players (`private.record_miss`, `runs.ts:330`), which needs an identity; answer 9 keeps answers only. The human confirmed (answer 19).

**The peek and pages.** After a run the guest sees their result and a "Make an account to keep your streak, see your friends and play today's game for points" panel over a drawn stand-in, blurred, of a streak, a friends board and a calendar (answer 15; made of fixed shapes, no fetch). Signing up goes through the existing sign-in, and then starts clean (answers 3 and 9). A guest who signs up the same day may play today's game for points (answer 14); no rule stops it, so nothing is built for it, but 18e's e2e proves it. Group invite pages (`src/app/(shell)/g/[code]/page.tsx`) keep sign-up first, with a "play today's game as a guest" link that goes to the front page. The front page's text "Sign in to play" (`src/app/(shell)/page.tsx`) gains a guest button for signed-out visitors. The privacy page changes before launch (see acceptance).

## Security changes proposed (for DECISIONS.md, reviewed before any code)
1. Player identity (Hard to reverse): replace "No anonymous or guest users" and the "Changing in M15" text. New text: sign-in is required for everything except guest play, which uses no account; a guest is a keyless run held by a hashed random token, never an `auth.users` row.
2. New tables `guest_run`, `guest_run_event`, `guest_question_open`, `guest_round_word`, `guest_round_reject` and `guest_tally`, each with RLS and one `plor_app` policy per command it is granted, no policy for other roles (as Row-level security in `private`); pgTAP checks that none references `auth.users` and none has a broadcast trigger.
3. Grants, no wider than the player ones (read 2026-11-11: baseline lines 2859 and 2875 give `plor_app` select and insert on `run`, `run_event` and `question_open`, and line 2861 select on `run_status`; `supabase/migrations/20261107105151_game_2_rounds.sql:46` gives it select alone on `round_word` and nothing on `round_reject`; the judge and the examples are `security definer` functions it may execute, line 261): `plor_app` may select and insert on `guest_run`, `guest_run_event` and `guest_question_open`, and select on `guest_round_word`, `guest_tally` and the `guest_run_status` view. It has **no** privilege on `guest_round_reject`, **no insert** on `guest_round_word`, **no delete** on any guest table, and **no write** on `guest_tally` (a trigger on `guest_run_event` makes the increments; narrower than the draft's "insert and update `n`"). Game 2's writes go through `private.guest_judge_word` and `private.guest_round_examples`, `security definer` functions with an empty `search_path` that share their rule code with `private.judge_word` and `private.round_examples` (one core both call, as for game 1's triggers), execute granted to `plor_app`. Rows are deleted by `private.end_guest_run` and `private.purge_guest_days` (Design, "When a guest run ends"), also `security definer`, execute granted to `plor_app`. The tally has no way to read a run, and nothing but the trigger can write it.
4. The shared order and clock rules become functions called by both sets of triggers, and game 2's judge and examples get a shared core (edits to the baseline's and the game 2 migration's functions).
5. Turnstile secret key: only in Vercel env vars and the human's password manager; `.env.local` and CI hold Cloudflare's published test keys only.
6. Guest routes read no Supabase session and set only the path-scoped guest cookie; no account route reads it (checked by test).
7. `readServerEnv` now needs three Turnstile variables, `TURNSTILE_SITE_KEY`, `TURNSTILE_SECRET_KEY` and `TURNSTILE_ALLOWED_HOSTNAMES` (answer 25).
